## 현재 확인된 사실과 아직 모르는 내용

- 1번 기존 `index.html`에는 `schemaVersion=1.1`, `width`, `depth`, 바닥 X-Z, 높이 Y, `walls`, `zones`, `importanceStrokes`, `router`와 내장 `WifiEngine.value()`가 있습니다. **공식 실내 외곽 다각형 `footprint`는 없습니다.**
- 2번 과거 전달사항은 `POST localhost:8000/simulate`와 `values[row][col]`뿐입니다. 최신 엔진 소스, 요청/응답 JSON, 배포 주소, CORS/보정 적용 여부 미확인.
- 3번 과거 전달사항은 측정 위치 X-Z(m), RSSI(dBm), 2.4/5GHz, 당시 공유기 위치 필요입니다. 최신 측정앱/보정 함수 반환 스키마 미확인.
- 4번 개발 API는 `POST /candidate-locations`, `POST /optimize`(backend/README.md). `/optimize`는 *후보마다 각 수신 위치에서 산출된 RSSI 배열*을 필수로 요구합니다. 2번·3번 데이터를 직접 계산하지 않습니다.
- 기존 `preview/stage3.html` 로컬 시연에서는 **v1.6 내장 JS 예상 RSSI**만 4번 API로 보내며, 2·3번 데이터로 가장하지 않습니다.

| 평면/높이/단위 | 바닥 X-Z(m), 위쪽 Y(m) | 미확정 |
| 실내 외곽 | `footprint:[[x,z],...]` 시계/반시계 방향, 구멍의 표현 | 미확정 |
| 콘크리트 벽 | `walls:[{x1,z1,x2,z2,heightM?}]` | 미확정 |

| 랜 포트 | 실측 `{x,z,y}`, 설치 가능 경로/최대 케이블 길이(m) | 미확정 |
| 중요도 | `+100/0/-100` 위치별 결과를 가져오는 API 또는 브러시/존 변환 | 미확정 |

## B. 2번 전파 예측 엔진 API 계약 (담당자 확인용)

아래는 **확정된 계약이 아닌 필요한 정보 예시**입니다.

```json
{
  "layoutRef": "layout-v1.1-example",
  "frequencyGHz": 5,
  "candidateRouterPosition": {"x": 1.5, "z": 1.25, "y": 1.2},
  "receivers": [
    {"x": 1.0, "z": 1.0, "y": 1.0},
    {"x": 2.0, "z": 2.0, "y": 1.0}
  ]
}
```

예상 결과 *형태의 제안* (위의 예시는 실제 2번 엔진에서 검증되지 않았음):

```json
{
  "frequencyGHz": 5,
  "routerPosition": {"x": 1.5, "z": 1.25, "y": 1.2},
  "receiverRssiDbm": [-56.2, -68.1],
  "predictionSource": "unverified-example"
}
```

**담당자에게 확인할 항목**
- 최신 저장소/파일/커밋 SHA, 실행 포트/실제 엔드포인트, 소스-테스트 쌍, HTTP 예외 응답.
- 엔진에 도면 전체를 전달하는지, 위치별 배치 요청을 지원하는지, 복수 후보 배치 일괄 예측이 가능한지.
- `values[row][col]`는 **행 z, 열 x**인가? `origin`, `gridStepM`, `cellAnchor=center`인지? 수직 Y와 화면 2D y축 혼동 금지.
- 신호 단위가 **dBm**, 대역이 **2.4/5GHz**, 같은 조건의 결과 결정론 여부.
- 보정 전/후 표시 필드, 모델 버전, 벽 종류별 경로 손실, `receiverY`, 실측 오차/기준값.
- 브라우저/로컬 통합 시 CORS 허용 출처와 타임아웃·재시도, 서버 운영(무료/유료 여부) 조건.

### 4번으로 연결할 확정 대상

`POST /optimize` 요청의 `candidates:[{position:{x,z,y},rssisDbm:[...]}]`은 **각 후보별 동일 `probes` 순서**여야 합니다. 2번의 `values[row][col]`만 있다면 좌표 매핑, 보간/샘플링, 결측 처리 규칙과 검증 샘플을 함께 제공해야 합니다.

## C. 3번 실측/보정 계약 (담당자 확인용)

제안 데이터 최소 예시 (더미 숫자, 실측 아님):

```json
{
  "measurementId": "synthetic-demo-only",
  "position": {"x": 1.0, "z": 2.0, "y": 1.0},
  "routerPositionAtMeasurement": {"x": 2.0, "z": 2.5, "y": 1.2},
  "frequencyGHz": 2.4,
  "rssiDbm": -65,
  "deviceClass": "android",
  "measuredAt": "2026-11-09T00:00:00+09:00",
  "isSynthetic": true
}
```

**담당자에게 확인할 항목**
- Android 측정 방식과 위치 입력의 오차, 측정 횟수/중앙값, 밴드 및 SSID/BSSID 익명화 기준.
- 측정 당시 공유기 위치 필수 여부, 단위·정확도·타임스탬프, 높이 측정 방식.
- 보정이 **RSSI 직접 보정**, 모델 파라미터 보정, 공간 바이어스 지도 중 무엇을 출력하는지.
- 보정 출력을 2번 예측 후보별로 적용 가능한지, 장치·대역·환경별 적용 범위/불확실도·버전.
- 빈 값/아웃라이어/측정 부재 시 보정 불가 표시, 개인정보 수집·저장 정책.
